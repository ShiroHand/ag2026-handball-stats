# アジア大会2026 ハンドボール スタッツダッシュボード

第20回アジア競技大会 愛知・名古屋 2026（ハンドボール）の試合データを
**公式リザルトシステムから自動取得**し、handball.ai のレポートに近い形で可視化する静的サイトです。

- ビルド不要（素の HTML / CSS / ES Modules、外部ライブラリなし）
- データは `data/` 配下の JSON。GitHub Actions が定期的に上書き更新します
- GitHub Pages でそのまま公開できます

---

## 画面

| ページ | 内容 |
|---|---|
| `index.html` | 大会トップ — 日程・結果、グループ順位表、得点/セーブランキング、チーム一覧 |
| `match.html` | 試合レポート — KPI、両チーム比較、攻撃内訳、シュートマップ（コート／ゴールマウス）、GK別セーブマップ、5分ごとの推移、選手別イベント（記号タイムライン）、選手スタッツ |
| `team.html` | チーム分析（攻撃）— 全試合を累積したスカウティングレポート、試合別推移、選手累計 |
| `defense.html` | 守備分析 — 対戦相手の攻撃データを合計した被シュートマップ、失点コース、相手の連携図、相手別守備成績、大会内守備ランキング |
| `situations.html` | 局面分析 — 攻撃回数・攻撃効率・リバウンド、数的状況別（均等/優位/不利）、無人ゴール、大会内効率ランキング |
| `analysis.html` | クラスター・因子分析 — 攻守効率の散布図、k-means分類、主成分分析（攻撃/守備/攻守） |

## セットアップ

### 1. GitHub にリポジトリを作る

```bash
git init
git add .
git commit -m "初期コミット: ハンドボールダッシュボード"
git branch -M main
git remote add origin git@github.com:<ユーザー名>/<リポジトリ名>.git
git push -u origin main
```

### 2. GitHub Pages を有効にする

リポジトリの **Settings → Pages → Build and deployment**
- Source: `Deploy from a branch`
- Branch: `main` / `/ (root)`

数分後に `https://<ユーザー名>.github.io/<リポジトリ名>/` で公開されます。

### 3. 自動更新を有効にする

**Settings → Actions → General → Workflow permissions** で
`Read and write permissions` を選択して保存してください（Actions がデータ更新をコミットするため）。

`.github/workflows/update-data.yml` が定期的に公式APIを取得し、
差分があれば `data/` を更新してコミットします。手動実行は
**Actions → 公式データ自動更新 → Run workflow** から。

### 画面上の「公式データを取り込む」ボタン

全ページのヘッダに更新バーがあります。

| 表示・ボタン | 動作 |
|---|---|
| `データ取得: ○分前` | いま表示しているデータが取得された時刻 |
| **表示を最新にする** | ページを再読み込みして、最新のコミット済みデータを表示 |
| **公式データを取り込む** | GitHub Actions の実行ページを別タブで開く。そこで `Run workflow` を押すと公式から取得が始まり、**完了を検知して元の画面が自動で更新される** |

ブラウザから公式APIを直接叩くことは CORS で拒否されるため、取得そのものは
GitHub のサーバー（Actions）が行います。ボタンはその起動と完了待ちを担当します。
GitHub API（公開リポジトリの参照）は認証不要で 60回/時 まで使えます。

より新しいデータが公開されている場合は、ページを開いた時点で
「より新しいデータがあります」と表示されます。

### 定時実行が動かないときは

GitHub の定時実行（cron）は**保証されていません**。特に `*/5` `*/10` のような
短い間隔は混雑時に丸ごと落とされ、一度も発火しないことがあります。
本リポジトリでは対策として、

- 半端な分にずらした15分おき（`4,19,34,49 1-17 * * *`）
- 毎時1回の保険（`52 * * * *`）

の2本立てにしています。それでも遅れる／動かない場合は、手元から実行してください。

```bash
./update.sh
```

`git pull` → 公式API取得 → PDF取り込み → 差分があればコミットして push まで一気に行います。
試合直後にすぐ反映させたいときはこちらが確実です。

> 大会が終わったら `cron` の行をコメントアウトするか、ワークフローを無効化してください。

## データを手元で更新する

Node.js 18 以上が必要です（依存パッケージなし）。

```bash
node scripts/fetch-data.mjs              # 全日程を更新
node scripts/fetch-data.mjs --day 2026-09-25   # 指定日のみ
node scripts/fetch-data.mjs --force      # 差分がなくても書き出す
node scripts/fetch-flags.mjs             # 国旗画像を取得（不足分のみ）
node scripts/fetch-reports.mjs           # 公式PDFレポート（7対6など）を取り込み
node scripts/fetch-photos.mjs            # 選手の顔写真を取得（不足分のみ）
node scripts/fetch-photos.mjs --all      # 出場していない選手も含めて取得
```

`fetch-reports.mjs` は PDF のテキスト化に `pdftotext`（poppler-utils）を使います。

```bash
brew install poppler          # macOS
sudo apt install poppler-utils # Ubuntu
```

ローカルで表示を確認するときは、`file://` ではなく簡易サーバ経由で開いてください。

```bash
python3 -m http.server 8000
# → http://localhost:8000/
```

## データ構造

```
data/
├── tournament.json          大会情報・日程・結果・順位表・チーム一覧（自動生成）
├── matches/<試合ID>.json     試合ごとの詳細スタッツ（自動生成）
└── manual/<試合ID>.json      手入力の戦術データ（自動更新で上書きされません）
```

試合ID は公式のユニットキーから生成されます（例: `M-GPB-000400` = 男子・予選グループB・第4試合）。
男子は `M-`、女子は `W-` で始まるため、全ページで男女を切り替えて表示できます。

### 守備データの考え方

守備専用のデータは公式APIに存在しないため、**対戦相手の攻撃データを合計**して守備指標を算出しています。

| 守備指標 | 算出元 |
|---|---|
| 被シュート位置マップ | 相手チームの位置別シュート（`teams.<相手>.shot`）の合計 |
| 失点コース（ゴールマウス） | 相手チームの `shotZone`（= 自GKが受けたコース）の合計 |
| GKセーブコース | 自チームの `gkZone` の合計 |
| 被決定率 | 相手の `GOALS` / `SHOTS` |
| 被速攻G・被BT G | 相手の `FB_GOALS` / `BT_GOALS` |

### `matches/*.json` の主な中身

| キー | 内容 |
|---|---|
| `teams.<略称>.stats` | チーム集計（`GOALS` / `SHOTS` / `EFFICIENCY` / `GK_SAVES` など） |
| `teams.<略称>.shot` | 位置別シュート `{LW,L6,C6,R6,RW,L9,C9,R9,P7,EG,BT,FB,FLY}` → `{g, s}` |
| `teams.<略称>.shotZone` | ゴールマウス 3×3（上→下 × 左→中→右）→ `{g, s}` |
| `teams.<略称>.gk` | GKの位置別被シュート → `{sv, s, g}` |
| `teams.<略称>.gkZone` | GKのコース別セーブ 3×3 → `{sv, s, g}` |
| `teams.<略称>.players[]` | 選手ごとの同じ構造 + `stats`（545項目から抽出） |
| `teams.<略称>.connections[]` | アシスト連携 `{fromBib, fromName, fromRole, toBib, toName, toRole, count, goals, zones}` |
| `teams.<略称>.posLinks[]` | ポジション間の連携 `{from, to, count, goals}`（LW/LB/CB/RB/RW/PV/GK） |
| `teams.<略称>.shots[]` | 1本ごとのシュート `{min, period, bib, name, role, zone, result, goalZone, assistBib, score}` |
| `teams.<略称>.defActs[]` | 守備アクション `{bib, name, blocks, steals, sevenMConceded, twoMin}` |
| `teams.<略称>.possessions` | `{attacks, goals, shots, missed, saves, turnovers, offReb, defReb, eff}` |
| `teams.<略称>.timeline[]` | 5分区切りの集計 `{bucket, attacks, goals, shots, missed, saves, turnovers, ...}` |
| `teams.<略称>.situations` / `situationsDef` | 数的状況別（`equal` / `up` / `down`）の攻撃時・守備時 |
| `teams.<略称>.emptyGoal` | 無人ゴールへのシュート `{shotsFor, goalsFor, shotsAgainst, goalsAgainst}` |

### プレーバイプレーから導出している指標

公式APIの `/{disc}/actions/Total/{ユニットキー}` に入っている
1プレーごとの記録から、以下を計算しています。

| 指標 | 導出方法 | 精度 |
|---|---|---|
| アシスト連携（誰→誰） | `ASS` アクションを、同じチームの次のシュートに結び付ける | 公式のアシスト総数と一致（277本中276本） |
| 攻撃回数 / 守備回数 | `ATTACK` アクションの数 | 公式記録そのもの |
| 攻撃効率 | 得点 ÷ 攻撃回数 | 計算値 |
| オフェンスリバウンド | 同一攻撃内で、セーブ／ポスト／ブロックの後に同じチームが撃った再シュート | **推定** |
| ディフェンスリバウンド | 相手の攻撃がセーブ／ポスト／ブロックで終わった回数 | **推定** |
| 数的優位 / 不利 | `TMS`（2分間退場）の記録時刻から±2分の区間を復元し、攻撃開始時点の人数差で分類 | 退場時刻は公式記録、区間は計算 |
| 5分ごとの推移 | 各アクションのタイムスタンプを5分で区切って集計 | 公式記録そのもの |

### 7対6（エンプティーゴール）

APIには7対6の攻撃回数が入っていませんが、**公式PDFレポート「Empty Goal Analysis」(C77)**
に完全な集計があります。`scripts/fetch-reports.mjs` がこれを取り込み、
`data/reports/<試合ID>.json` に保存します。

| 取り込む内容 | 中身 |
|---|---|
| `emptyGoal.situations` | 7対6 / 6対6 / その他ごとの 攻撃回数・得点・セーブ・ミス・ブロック・ポスト・ターンオーバー・成功率・被無人ゴール |
| `emptyGoal.timeline` | 上記の5分ごとの発生（得点/攻撃） |
| `emptyGoal.duration` | 攻撃時間別（<15秒 〜 >60秒）の 得点/攻撃 |
| `emptyGoal.substitutions` | GK↔コートプレーヤーの交代回数（7人攻撃への切替回数） |
| `teamStats` | 公式の Number of Attacks と Scoring Efficiency（C83） |

公式の攻撃回数とプレーバイプレー由来の攻撃回数は一致することを確認済みです
（KOR-KUW戦: 公式46/47 対 導出46/47）。

### Equality / Superiority / Inferiority

公式PDFには含まれていない指標です（handball.ai のレポート独自）。
本ダッシュボードでは `TMS`（2分間退場）の記録時刻から前後2分の区間を復元し、
各攻撃の開始時点の人数差で分類して同等の表を作っています。

## 取得元について

公式リザルトの内部API（`https://back.results.asiangames2026.org/s/AG2026/en/...`）を利用しています。
レスポンスは zlib deflate ストリームが latin1→utf8 で再エンコードされた形で返るため、
`scripts/fetch-data.mjs` 内でバイト列に戻してから展開しています。

主なエンドポイント:

| パス | 内容 |
|---|---|
| `/HBL/disc/data` | 競技情報・開催日・種目 |
| `/HBL/schedule/daily/<日付>` | 日別の試合一覧（エントリー含む） |
| `/HBL/results/<ユニットキー>` | 試合結果・チーム/選手スタッツ |
| `/HBL/groups/<種目キー>` | グループ順位表 |
| `/HBL/brackets/<種目キー>` | 決勝トーナメント表 |

API 仕様が変わった場合は `scripts/fetch-data.mjs` の該当箇所を調整してください。

## 選手別イベント（記号タイムライン）

試合レポートの「選手別イベント」は handball.ai と同じ考え方で、
1行＝1選手、横軸＝試合の経過時間として出来事を記号で並べたものです。

| 記号 | 意味 | 元になる公式データ |
|---|---|---|
| ● 緑 | ゴール | シュートアクションの結果 GOAL |
| ⑦ 緑 | 7mゴール | PTY + GOAL |
| Ⓖ | GKのゴール | GK登録の選手のゴール |
| Ⓐ | アシスト | ASS アクション |
| Ⓧ | ノーゴール（セーブ・ポスト・枠外） | シュートアクションの結果 SAVE / POST / MISS |
| ⑦ 赤 | 7m失敗 | PTY + GOAL以外 |
| ● 黒 | ミス（ロストボール・テクニカル） | TO / TFT |
| Ⓢ 紫 | スティール | ST |
| Ⓑ | ブロック | BLC |
| Ⓟ | 7mを与えた | FRP |
| ② | 2分間退場（帯で2分間を表示） | TMS |
| Ⓢ 緑 / ● 赤 | GKセーブ / GK失点 | 相手のシュートアクションに付く GK 登録番号から復元 |

GKの登録番号は結果JSONの出場選手一覧には入っていないため、
「そのGKが浴びた失点数・セーブ数」を公式の個人スタッツと突き合わせて特定しています
（`gkRegMap()`）。突き合わせ結果は公式値と一致することを確認済みです。

## 選手の顔写真

公式の設定API（`/s/AG2026/en/config`）が返す `photoPath` 配下に
`<選手登録番号>.jpg` として置かれています。
`scripts/fetch-photos.mjs` がこれを `assets/photos/` に取り込み、
`data/entries.json`（エントリー名簿）で氏名 → 登録番号を引いて表示します。
写真が無い選手は頭文字のバッジで代替されます。

## KPI（試合レポート上部）

| 指標 | 計算 |
|---|---|
| 攻撃回数 | 公式PDF（C83）の Number of Attacks。無ければプレーバイプレーの `ATTACK` から算出 |
| 得点 | 公式 `GOALS` |
| ターンオーバー | プレーバイプレーの `TO` / `TFT` |
| 攻撃効率 | 得点 ÷ 攻撃回数 |
| ターンオーバー率 | ターンオーバー ÷ 攻撃回数 |
| シュート数 | 公式 `SHOTS` |
| 枠内シュート | プレーバイプレーの結果 GOAL + SAVE |
| 枠外・ポスト | 同 POST + MISS |
| アシスト | `ASS` アクション |
| アシスト率 | アシスト ÷ 得点 |

**枠内 + 枠外 + 被ブロック = 公式のシュート数** になる。
ブロックされたシュートはプレーバイプレーにシュートとして残らないため、
個人スタッツの `BLOCKED` を足して辻褄を合わせている（シュート数タイルの補足に内訳を表示）。

5分ごとの推移にも攻撃効率とアシスト率を入れている。割合は足し算できないので、
区間ごとに分子÷分母で出し、「計」の列だけは合計どうしの比で出している。
分母が0の区間は表では `–`、グラフでは線を切る。
攻撃回数は推定値なので、区間によっては得点が攻撃回数を上回り100%を超えることがある
（縦軸はその場合だけ50%刻みで上に伸ばす）。

## 割合の事前確率補正（経験ベイズ）

5分間の攻撃回数は3〜5回しかないため、実測の割合はほとんど運の揺れになる
（1本決めれば100%、外せば0%）。そこで大会全体からベータ分布を推定し、縮小推定する。

```
補正後の割合 = (分子 + k × 事前平均) / (分母 + k)
```

- **事前平均**: そのチームの大会成績（攻撃40回以上あるとき）。足りなければ男女別の全体平均。
- **k**: 事前分布を「何回分の試行」とみなすかの重み。`scripts/fetch-data.mjs` の
  `fitPrior()` がモーメント法で推定する。区間ごとの散らばりのうち二項分布の揺れでは
  説明できない分（＝本当の実力差）が大きいほど k は小さくなり、実測を尊重する。
  推定値は `data/tournament.json` の `priors` に男女別で入る。

グラフは **実線＝補正後 / 破線＝実測** の二重表示。表にも「（実測）」「（補正後）」の
両方の行を出している。累積グラフでは、序盤ほど事前分布に近く、試合が進むほど実測に寄る。

注意: この補正が直すのは**ばらつき**であって**偏り**ではない。攻撃回数の数え方に
系統的なずれがあれば、補正後の値も同じだけずれる。

## 攻撃回数の下限

公式の `ATTACK` アクションは速攻のときに記録されないことがあり、
得点数より攻撃回数が少ない（＝効率100%超）試合が出る。
得点1本とターンオーバー1本はそれぞれ別の攻撃なので、これは論理的にありえない。

そこで各5分区間で **`得点 + ターンオーバー` を下限**として補い、試合合計はその区間の
合計に揃えている（表の「計」と一致させるため）。14試合中3試合で下限が働いた。
公式PDFで攻撃回数が分かる試合ではほぼ影響しない（KOR 46→47、KUW 47→47 で検証）。
KPI タイルは公式PDFの値があればそちらを優先する。

## 50回あたりの得点・失点

攻撃回数は試合ごと・チームごとにばらつくため、得点の絶対数だけでは攻守の質を比べられない
（テンポの速いチームは得点も失点も増える）。そこで攻撃50回に換算した値を出している。

```
50攻撃あたり得点 = 得点 ÷ 攻撃回数 × 50   （= 攻撃効率 × 50）
50守備あたり失点 = 失点 ÷ 被攻撃回数 × 50 （= 被攻撃効率 × 50）
差引            = 上のふたつの差
```

ハンドボールの1試合はおおよそ50攻撃なので、「1試合あたり何点」に近い感覚で読める。
差引はチーム力の要約として使える（バスケの net rating と同じ考え方）。

**表示場所**

| ページ | 内容 |
|---|---|
| `index.html` | 大会内の全チームを差引の降順で一覧 |
| `match.html` | 両チームのKPIタイル（相手の攻撃回数を守備側の分母に使う） |
| `team.html` | 全試合累計。守備側は対戦相手の攻撃を合計 |
| `defense.html` | 同上（守備側を主役にした言い方） |
| `situations.html` | 上部KPI・試合ごとの表・大会内ランキング |

## ポジション別の50回あたり得点

シュート位置の図（`courtMap`）の各位置に、**50回の攻撃あたりその位置から何点取れているか**
を併記している（分母はチームの総攻撃回数／守備側は総被攻撃回数）。

```
位置ごとの値 = その位置のゴール数 ÷ 総攻撃回数 × 50
```

### 位置が定まらない攻撃の扱い

速攻（FB）・ブレイクスルー（BT）・フライング（FLY）はコート上の1点に置けないが、
これを図から外すと合計が KPI と合わなくなる。そこで**コート図の下に別枠の帯**を設け、
同じ色スケール・同じ表記で並べている。

これでコート10箇所＋別枠の合計が、必ず KPI の「50攻撃あたり得点」と一致する。
図のキャプションにも `得点77 ÷ 111回 × 50 = 34.7` のように計算式を出している。

公式データ上、シュートは13ゾーン（コート10 + BT/FB/FLY）のいずれか1つに必ず分類され、
全ゾーンの合計は公式の GOALS / SHOTS と完全に一致することを確認済み。

### 内訳表

図と同じ数字を `zoneBreakdownTable()` が表にする。列は
**得点 / シュート / 決定率 / 50回あたり / 得点の構成比**で、
「コート上」と「位置が定まらない」でグループ分けし、最後に合計行（構成比100%）を置く。
守備側は「失点 / 被シュート」と言い換える。

この表があると、たとえば「速攻が総得点の26%（50攻撃あたり9.0点）を占めている」
といった、コート図だけでは見えない構成が読める。

### 注意

チーム分析ページの守備側マップは、以前は GK の個人スタッツ（`gk` マップ）から作っていたが、
集計キーの重複で失点が過大（40失点が55と表示）になっていたため、
**相手チームのシュートマップの合計**に統一した（守備分析ページと同じ作り方）。

## 対象試合フィルター（チーム分析・守備分析）

両ページの上部に、そのチームの試合を並べたチップが出る。クリックで集計対象を出し入れでき、
ページ全体（KPI・シュートマップ・内訳表・連携図・選手スタッツ）がその場で再計算される。

- 選択は URL の `m=` に入る（例 `team.html?team=BRN&m=M-GPA-000100,M-GPA-000300`）。
  絞り込んだ状態のままリンクを共有できる。全試合のときは `m=` を付けない。
- 「全選択」「直近1試合」のボタンつき。最後の1試合は外せない（0件集計を防ぐため）。
- チームや男女を切り替えると絞り込みは解除される。
- **大会内ランキングは絞り込みの影響を受けない**（`defAgg(code, useFilter)` の第2引数で制御）。
  他チームの数字まで巻き添えで絞られると比較にならないため。

実装は `assets/js/matchfilter.js`。

## net rating（差引）

| 50守備あたり失点 | 相手の攻撃効率 × 50 |
| 差引（50回あたり） | 上のふたつの差。バスケの net rating と同じ考え方 |

## クラスター・因子分析（`analysis.html`）

統計処理は `assets/js/stats.js` に自前で実装している（外部ライブラリ無し）。
既知の2因子構造をもつ人工データで、負荷量・固有値・クラスタ復元を検証済み。

### 散布図とクラスター分析

横軸 50攻撃あたり得点 / 縦軸 50守備あたり失点。
**縦軸は反転**してあり、上にいくほど失点が少ない。したがって右上ほど強い。
平均線で四象限に割り、総合力型／撃ち合い型／守備型／苦戦型を示す。

分類は2変数を標準化して **k-means**（k-means++ 初期化・25回リスタート・固定シード）。
分類数は 2/3/4 から選べる。分かれ具合は**シルエット係数**で表示する
（0.5超=はっきり、0.25超=ゆるやか、それ以下=ほぼ分かれていない）。
クラスタ名は攻守の平均からの乖離（σ単位）で決め、同名が出たら差引順に「上位／下位」を付ける。

### 主成分分析（因子分析）

**攻撃のみ（8変数）／守備のみ（7変数）／攻守まとめて（15変数）**の3通り。
相関行列をヤコビ法で固有値分解し、負荷量 = 固有ベクトル × √固有値。

観測単位は**チーム×試合**（チーム単位だと10点前後しかなく推定できないため）。
男女で水準が違うので**男女それぞれの中で標準化してから合わせる**。
選択中のカテゴリの絞り込んだ試合に、もう一方のカテゴリの全試合を足して標本を稼ぐ。

#### 標本数についての注意（重要）

因子分析は「標本数 ÷ 変数の数」が5倍以上ほしいが、この大会の規模では届かない。
`adequacy()` が実際の比率を計算し、カードの上に色付きで表示する。

| 分析 | 変数 | 標本 | 比率 | 扱い |
|---|---|---|---|---|
| 攻撃のみ | 8 | 28 | 3.5倍 | 大枠の傾向のみ |
| 守備のみ | 7 | 28 | 4.0倍 | 大枠の傾向のみ |
| 攻守まとめて | 15 | 28 | 1.9倍 | 参考程度 |

**負荷量の細かい数値や順位は、試合が増えると動く。**
第1・第2主成分がどの変数で構成されているか、という大枠の読み方に留めること。
試合を絞り込むとさらに標本が減るので、表示される比率を必ず確認する。

### 試合フィルター

`allMatchFilterCard()`（`matchfilter.js`）。日付ごとにまとめて出し入れできる。
選択は URL の `m=` に入るので共有可能。散布図・分類・因子分析のすべてに反映される。

## 攻守の切り替え（トランジション）

「直前の攻撃がどう終わったか」で、次の攻撃の成否がどう変わるかを数える。

| 終わり方 | 中身 |
|---|---|
| `TO` | ミスでボールを失った（`TO` / `TFT`）|
| `GOAL` | ゴールを決めた |
| `SAVE` | シュートがGKにセーブされた |
| `POST` | シュートが枠外・ポスト（`BLC` もここに含める）|

各チームに2方向を持たせる（`teams.<code>.transitions`）。

- `afterOwn[T]` … 自分の攻撃が T で終わった直後、相手の攻撃 →「自分の失点」
- `afterOpp[T]` … 相手の攻撃が T で終わった直後、自分の攻撃 →「自分の得点」

それぞれ以下を持つ。

| 項目 | 中身 |
|---|---|
| `n` | 切り替えの回数 |
| `goals` | 次の攻撃での得点 |
| `shots` | 次の攻撃がシュートまで到達した数（TOで終われば未到達）|
| `fast` / `fastGoals` / `fastSecs[]` | 速攻（FB）の本数 / 得点 / 所要秒の生データ |
| `second` / `secondGoals` / `secondSecs[]` | 2次速攻（FBでないが20秒以内）の本数 / 得点 / 所要秒 |
| `set` / `setGoals` / `setSecs[]` | セット攻撃（20秒超）の本数 / 得点 / 所要秒 |
| `bt` / `btGoals` | ブレイクスルー（BT）の本数 / 得点。速さとは別の軸なので参考値 |

**秒数は合計と件数ではなく生の値の配列で持つ。**
中央値は平均と違って後から合算できないため、試合をまたいで集計したり
フィルタで試合を絞ったりするには元の値が要る。
1チーム1試合あたり50個程度で、`data/matches` 全体でも 2.7MB に収まる。
表示は**中央値**（外れ値に引きずられないため）、平均は数値にカーソルを合わせると出る。

UIでは **回数 / 得点(失点) / 率 / 50回あたり / 速攻率 / 平均秒 / 全体に占める割合** を出す。

「50回あたり」の分母は KPI と同じで、**得点はチームの総攻撃回数・失点は総守備回数**
（= 相手の総攻撃回数）。その状況の発生回数ではないので注意。
これにより「速攻からの得点が50攻撃あたり何点ぶんか」という形で、KPI と同じ土俵で読める。

合計は KPI の「50回あたり」より少し小さくなる。
ハーフ最初の攻撃など、直前の攻撃が無い攻撃は切り替えに含まれないため
（検証例: KPI 34.7 に対し切り替え合計 30.18、差の4.5が非切り替えの得点）。

### 数え方の要点

**`ATTACK` アクションは使わない。** 速攻のときに `ATTACK` が記録されないことがあり、
切り替えの分析では速攻こそが本丸なので、そこを落とすと意味がなくなる。
代わりに**シュートとターンオーバーの「結末」だけを時系列に並べ**、
持ち主が入れ替わったところを切り替えとして数える（`buildTransitions()`）。

- 同じチームの結末が続く場合はオフェンスリバウンドなので切り替えにしない。
- ハーフタイム（`ENDP`）をまたぐ連鎖は切る。
- 結果として、**ハーフ最初の攻撃など「直前の攻撃が無い」ものは集計に入らない**。
  そのため切り替えで数えた得点の合計は、公式の総得点よりやや少なくなることがある
  （検証した試合では KOR 26/26 で一致、KUW 20/23）。

対称性の検証: A の `afterOwn` と B の `afterOpp` は必ず一致する（同じ事象を両側から見たもの）。

### 配色について

サイトのシュートマップは「赤＝決定率が高い＝良い」だが、失点率は逆に読む。
この表だけは**良し悪しそのものを色にする**（緑＝良い / 赤＝悪い）ので、
失点率20%は緑、失点率54%は橙になる。`goodColor()` が担当。

### 表示場所

| ページ | 内容 |
|---|---|
| `match.html` | 試合ごと、両チーム分 |
| `team.html` / `defense.html` / `situations.html` | 選択中の試合の累計 |
| `index.html` | 大会内の全チームを一覧（左半分＝失点率、右半分＝得点率）|
| `analysis.html` | 因子分析の変数に追加（攻撃に2つ・守備に2つ）|

因子分析には個別4状況ではなく、回数が確保できる2つにまとめた率を入れている
（`transVars()`: ミス直後 / シュートが枠に行かなかった直後）。
変数が増えたぶん標本比は下がるので、カード上部の表示を必ず確認すること。

## ターンオーバーの「痛さ」（forced/unforced の代わり）

forced / unforced の区別は公式データからはできないことを確認済み（後述）。
代わりに、**ターンオーバーの後に何が起きたか**を測る。こちらは定義が明確で推測を含まない。

- **速攻率** … 次の攻撃のシュートのうち、速攻（FB）だった割合
- **シュートまでの秒** … 速攻とそれ以外に分けた平均（混ぜると実態が見えない）
- **速攻の得点内訳** … 速攻で決まった得点を、直前の終わり方（ミス / 得点 / セーブ / 枠外・ポスト）で分解

### 速攻の定義と BT の扱い

当初は速攻に `BT`（ブレイクスルー）も含めていたが、切り替えからシュートまでの
所要時間を実測したところ、速攻と呼べる分布ではなかった。

| アクション | n | 中央値 | 10秒以内 |
|---|---|---|---|
| `FB` 速攻 | 137 | **9秒** | **67%** |
| `EG` 無人ゴール | 11 | 10秒 | 55% |
| `BT` ブレイクスルー | 190 | **29秒** | 11% |
| `RW` 右ウイング | 89 | 30秒 | 9% |
| `CSD` センター6m | 119 | 31秒 | 6% |
| `CLD` センター9m | 161 | 35秒 | 4% |

BT はセット攻撃のシュートとほぼ同じ分布。「1対1で抜いた」という意味であって
速いかどうかとは無関係なので、**速攻は `FB`（と定義上存在する `FBAG`）のみ**とした。

### 次の攻撃の速さは3つに分かれる

公式が速攻と記録するのは `FB` だけだが、FB でない攻撃の所要時間を実測すると
**明確な二峰性**があった。10〜15秒に鋭いピーク、20秒前後の谷、30〜40秒の山。

谷の位置（幅3秒・移動平均3で平滑化）:

| 直前の終わり方 | 谷 |
|---|---|
| セーブ後 | 21-24秒 |
| 枠外・ポスト後 | 18-21秒 |
| ミス後 | 21-24秒 |
| 失点後 | 15-18秒 |

前の山は、GKのアウトレットやスローオフから素早く攻めた**2次速攻**にあたる。
そこで **20秒**をしきい値に3つの帯へ分ける（`SECOND_WAVE_SEC`）。

| 帯 | 本数 | 得点 | 決定率 | 中央値 |
|---|---|---|---|---|
| 速攻（FB）| 137 | 110 | **80%** | 9秒 |
| 2次速攻（20秒以内）| 211 | 150 | **71%** | 13秒 |
| セット攻撃（20秒超）| 754 | 443 | **59%** | 37秒 |

中央値が 9 / 13 / **37** 秒と第2帯と第3帯のあいだが大きく空いており、
決定率も 80 / 71 / 59% と段階的に下がる。単なる「速い方の裾」ではなく別の局面といえる。

**20秒は実測の谷から選んだしきい値であって、公式の定義ではない。**

直前の終わり方別（相手の攻撃がこう終わった直後の自分の攻撃、14試合）:

| 直前 | 速攻 本/点(率) | 2次速攻 本/点(率) | セット 本/点(率) |
|---|---|---|---|
| ミス後 | 78/61 (78%) | 43/35 (81%) | 73/53 (73%) |
| 失点後 | 12/7 (58%) | 80/50 (63%) | 471/248 (53%) |
| セーブ後 | 28/25 (89%) | 61/45 (74%) | 113/82 (73%) |
| 枠外後 | 13/12 (92%) | 22/16 (73%) | 56/38 (68%) |

### BT はこの軸に出さない

一度 速攻 / BT / セット攻撃 の3分類にしたが、これは誤りだった。
**BT はセット攻撃の中で起きるものであって、速攻の対義ではない。**
この表の軸は「次の攻撃がどれだけ速かったか」の一本なので、BT を並べると
速さの軸とシュートの質の軸が混ざる（最初に BT を速攻に入れて
「速攻率40%・平均18.7秒」という矛盾を出したのと同じ種類の誤り）。

BT はどの帯にも現れうるので、この表には出さず、参考値として
データには残している。BT のシュート内訳は「位置別の内訳」の表
（`zoneBreakdownTable`）の `位置が定まらない` グループにある。

読み取れること:

- ターンオーバー直後は**3分類すべてで決定率が76〜78%**と高い。速攻だけの話ではなく、
  ポゼッション全体が有利になる。
- 失点直後はセット攻撃の決定率が51%まで落ちる（スローオフから守備が整うため）。
  速攻も2%しか出ない。
- セーブ後・枠外後は本数こそ少ないが、速攻の決定率が89〜92%と突出する。

表示場所は攻守の切り替えカードと同じ（`match.html` / `team.html` / `defense.html` /
`situations.html` / `index.html` / `analysis.html`）。
`team.html` と `defense.html` には**試合ごとの一覧**（`fastPerMatchCard()`）も置いている。

### forced / unforced ができない理由（調査記録 2026-09-25）

31試合・602件のターンオーバーを公式APIで全数調査した結果:

1. **種類を示す項目が全件で空。** `ActionAdd` / `Comment` / `Result` / `ResultDesc` /
   `When` / `Loc` / `X` / `Y` / `Z` / `Line` すべて 0件。値が入る拡張は表示用の `ActionMinute` のみ。
2. **記録システムに区別が無い。** アクション定義93件のうち `TO` は `ShowActionAdd = 0`
   （記録係の画面に種類欄が出ない）。オフェンシブファール・パスミス・オーバーステップ等の
   専用コードも存在しない。ターンオーバー系は `TO` と `TFT`（ベンチ）の2つだけ。
3. **プレーバイプレーの並びにも手がかりが無い。** TOの直前は81%が自チームの `ATTACK` のみで、
   攻撃開始とTOの間に中間イベントが一切入らない。判別に使えそうな直前イベントは
   相手の `ST`（14件）と `BLC`（7件）の計21件＝3.5%だけ。
4. **スティールとの対応も不成立。** ST 96件 / TO 602件。同一秒での一致は0件、±5秒でも44件。
   独立に記録されており連動していない。

→ 真の forced/unforced が必要なら映像からの手入力（`data/manual/`）しかない。
